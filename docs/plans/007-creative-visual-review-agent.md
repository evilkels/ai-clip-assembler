## Why this matters

The current agent is text-only and stateless. It receives raw candidate/timeline
JSON, is forced to answer in one short sentence, and never sees Frame Samples.
The Version gallery is generated by fixed frontend recipes, so the "creative
agent" does not actually choose footage or construct alternatives. After plan
005 supplies a rich Candidate Clip pool and plan 006 supplies conversation
history, the agent can compare visual moments and propose coherent complete cuts
while deterministic technical analysis remains responsible for motion quality.

## Target design

Use deterministic code for technical filtering and validation; use Pi for
semantic visual judgment and creative sequencing.

The agent receives:

- recent persisted conversation plus a bounded rolling summary
- Candidate Clip IDs, filenames, Scene IDs, timecodes, technical scores, and
  Clip Reasons
- a bounded, labelled set of representative Frame Samples spanning distinct
  Scenes/candidates
- current Timeline Document and existing Version choices

It may return:

- a conversational message
- zero or one validated Operation Proposal
- two to four validated preview-spec Versions with title, vibe, rationale,
  profile, and ordered items

Never trust model IDs, bounds, speeds, transforms, or counts. Validate all model
output against Candidate Clips and source durations before persisting/rendering.

## Steps

### Step 1: Add a shared validated Version model

Define backend Pydantic equivalents of `Version` and `VersionItem`, using the
same field names as TypeScript. Add a validator that receives the Candidate
Clip registry and enforces:

- 2-4 Versions, each with at least one item
- known `source_clip_id`, matching file ID/name
- item bounds within source video and within the Candidate Clip unless the
  existing extend semantics are explicitly requested and validated
- positive duration, supported profile, safe speed, valid transform
- recomputed `total_duration_sec` rather than trusting the model
- no duplicate `version_id`; server generates stable IDs if absent

Tests must reject hallucinated IDs, out-of-range bounds, invalid speed/
transform, empty versions, and wrong totals.

**Verify**: review-agent focused tests pass.

### Step 2: Build bounded visual and conversational context

Replace raw JSON truncation with a context builder that deliberately selects:

- recent Review Messages up to a documented count/token/character budget
- a persisted rolling summary for older turns
- Candidate Clips diversified by Source Video and Scene, then score
- representative Frame Samples labelled with candidate ID, filename, Scene,
  and timecode

Attach no more than 12 images per model call. Prefer first/middle/last coverage
for a Version candidate while maximizing Scene diversity across the project.
Deduplicate identical frame paths. Keep absolute paths in the transient Pi
command only; never persist them in Review Session JSON.

Update Pi's scoring prompt so still frames contribute Visual Interest Score,
subject/composition/progression/tags only. Remove any claim that still images
can establish motion smoothness; retain deterministic Smoothness Score in the
context.

**Verify**: unit tests assert image cap, deterministic selection, Scene
diversity, no paths in persisted sessions, and history summarization behavior.

### Step 3: Extend structured agent output

Extend the model response schema to include `message`, `operations`, and
`versions`. Give Pi explicit editorial goals: visual progression, avoiding
redundancy, coherent pacing, truthful rationale, filenames/timecodes instead of
UUIDs in prose, and respecting the Editor's prior feedback.

Parse and validate with typed models. If Operations are invalid but Versions
are valid, retain the valid Versions and explain the dropped Proposal. If all
model output is invalid/unavailable, return the deterministic
`mockVersions.ts`-equivalent fallback and existing graceful chat message. Never
apply an Operation automatically.

Persist the validated Versions on the agent Review Message using plan 006's
reserved structured payload.

**Verify**: injected-agent tests cover full success, chat-only, versions-only,
partial invalid output, total failure fallback, and conversation-dependent
follow-up ("make the second one faster" references prior Versions).

### Step 4: Replace the frontend mock as primary producer

Expose Versions through the Review Session/turn API. Update `Review.tsx` so the
latest agent-proposed Versions feed `VersionGallery`. Keep `proposeVersions` as
the explicit deterministic fallback for Manual Harness and model failure, not
the normal Pi path.

When a new chat turn returns Versions, update the gallery without remounting the
conversation. Preserve `replace_timeline` adoption unchanged. Display loading,
fallback, and validation-error states without discarding the previous valid
Versions.

**Verify**: frontend gates pass; E2E uses an injected response to assert model
Version titles/rationales appear and adoption still creates the expected
Timeline Items.

### Step 5: Verify privacy boundary and document the new roles

Ensure only projects explicitly analyzed with `pi_agent` attach Frame Samples
to Pi. Manual Harness projects must use deterministic Versions and make zero Pi
calls. Preserve the current local paths/cache behavior and do not log prompt
payloads or image contents.

Update architecture and harness docs: deterministic analysis owns Motion
Stability; Pi owns semantic visual curation and optional creative Versions;
Review Session supplies memory; all mutations remain Proposals.

Run all gates.

## STOP conditions

- Plans 005 or 006 are not complete or lack the promised pool/session contracts.
- More than 12 images are required for acceptable context; report measurements
  before increasing data/cost.
- Frame Samples would be sent for a Manual Harness project.
- Version adoption would need persisted parallel Timeline Documents; the locked
  design uses preview specs plus atomic replacement.
- Model output cannot be validated independently of prose/prompt compliance.
- A verification command fails twice after a reasonable fix.

## Maintenance notes

Changing prompt/model invalidates the existing Pi score cache. Reviewers should
focus on privacy mode, context bounds, hallucination rejection, deterministic
fallback, and whether follow-up requests genuinely use persisted history rather
than only the latest message.
